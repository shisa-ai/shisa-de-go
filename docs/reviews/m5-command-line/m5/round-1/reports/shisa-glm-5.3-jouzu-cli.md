# Review Report

## Summary

The M5 command line is a faithful port of `shisa_de/cli.py` under the DE-2-only scope. I checked `cmd/shisa-de/` against the Python reference (`shisa_de/cli.py` at the pinned revision), the `pyjson.go` options against `json.dumps` semantics, the four exported identifiers, the tests, and the documentation claims in `docs/PORT.md` and `README.md`.

What holds up:

- `doctor`, `ask` and `explain` reproduce the reference's text layout, JSON forms, streams (results to stdout, errors to stderr) and exit statuses. The report key order (`reportOrder`) matches Python's `health` insertion order exactly, and `doctor --json` correctly restores it with `indent=2, ensure_ascii=True`; `ask` correctly uses `indent=2, ensure_ascii=False`.
- `PythonJSONWith` is `json.dumps`: the `, `/`,` separator switch under indent, empty containers staying inline, `indent=""` distinct from `indent=None`, `: ` always the key separator, DEL and the C1 block escaped under `ensure_ascii`, astral code points as UTF-16 surrogate pairs. The 264-case fixture is generated by CPython 3.14.6 with sha256 provenance, and `TestPythonJSONIndentIsNotGoIndent` is a working negative comparator against `json.MarshalIndent`.
- `bestCode` reproduces `max(probabilities, key=...)` faithfully: `read_codes` reorders logprobs into slot order before softmax in both implementations (verified in `readout.py:583-585` and `readout.go:794-800`), so first-max-tie-break over slot iteration is Python's choice, and the "missing code is not a zero-probability candidate" rule matches Python's `max` over the dict's own keys.
- `stateFrom` is correct on all three readings of `--state` (absent → built-in example with Python's key order, JSON-looking text → decoded with int/float kept apart, everything else including malformed `{`-prefixed text → the text itself), and the `--state ''` distinction is structurally sound via `optionalStringValue`.
- The `.gitignore` anchoring works: the index tracks all seven `cmd/shisa-de/*.go` files plus `scripts/gen_pyjson_dumps.py` and both `testdata/pyjson_dumps*` files, and nothing else in the tree matches the ignore patterns (`*.out`, `*.exe`, `*.test`, `tokenizer.json`, `/tmp/`, `/bin/` produced no false positives).
- The exported seams (`PythonJSONWith`, `PythonStr`, `PythonRepr`, `Readout.MaxLogprobs`) are all documented for the CLI's use and do not expose internals a second consumer would misuse.

No HIGH or MEDIUM findings. The findings below are LOW: mostly undocumented divergences from the reference (the port's own rule is that every deliberate difference is recorded in PORT.md) and two comment/test-accuracy issues.

## Findings

### LOW: `explain` takes the read before printing, which is not Python's order, and the test comment claims it is
- Severity: LOW
- Confidence: HIGH
- Location: cmd/shisa-de/explain.go:74-77, cmd/shisa-de/main_test.go:801-826
- Problem: In Python (`cli.py::_explain`), the boundary check runs before any print, but sections 1 and 2 (the prompt and the slots) are printed *before* `readout.read_codes` is called. Go moves the read ahead of all printing. On the success path this is invisible (confirmed by the live diff), but on a read failure (e.g. an HTTP error from the server) Python shows the prompt and the slots before failing, and Go shows only an error line — the diagnostic value of a half-walkthrough is lost. This is a deliberate change per the code comment, but it is not in PORT.md's "Deliberate differences" section, and the test comment says "which is the Python command line's order", which is false for the read. The test itself (a tokenizer that cannot tokenize the terminator) fails at `CheckCodeBoundary`, which is before the first print in *both* implementations, so it proves the boundary path prints nothing — not the read path.
- Recommendation: Either document the ordering difference in PORT.md (it is a real, defensible divergence) or move the read back to after section 2's print to match Python. In the same change, correct the test comment, and consider a second test that fails the read itself (a stub returning a 500) to pin the read-failure behavior the reorder was made for.

### LOW: `shisa-de help` exits 0 where argparse exits 2
- Severity: LOW
- Confidence: HIGH
- Location: cmd/shisa-de/main.go:50, cmd/shisa-de/main_test.go:379
- Problem: The Python command line's subparsers are `doctor`, `ask`, `explain`; a bare `help` argument is an invalid choice and argparse exits 2. Go accepts `help` as a synonym for `--help` and exits 0, and `TestRunDispatch` pins that as intended. `-h`/`--help` matching argparse is fine; the bare-word `help` is a divergence, and it is not recorded in PORT.md.
- Recommendation: Either record it in PORT.md's command-line differences, or drop the bare-word form so an unknown word is uniformly exit 2.

### LOW: The flag grammar is not argparse's, and the deviations are undocumented
- Severity: LOW
- Confidence: MEDIUM
- Location: cmd/shisa-de/main.go:185-190 (family), cmd/shisa-de/flags.go:49-62 (optionalBool)
- Problem: Three small grammar mismatches with the reference: (1) argparse's `choices=FAMILIES` accepts exactly `de1`/`de2`, while Go routes `--family` through `NormalizeFamily`, so `--family DE-2` or `--family de_2` is accepted where Python exits 2; (2) `argparse.BooleanOptionalAction` takes no value, so `--reasoning=true` exits 2 in Python, while Go's `BoolFunc` accepts `--reasoning=true` and `--no-reasoning=false`; (3) the reverse direction — argparse allows unique prefix abbreviation (`--fam` → `--family`), Go does not. `--policy`/`--reads` use exact membership and are faithful. None of this is in PORT.md.
- Recommendation: Record the grammar differences in PORT.md (the simplest honest statement: "the flag layer is Go's `flag`, not `argparse`; values are checked after parsing, aliases argparse rejects are accepted, and abbreviation is not"), or tighten `--family` to exact match in the CLI layer.

### LOW: `--compound` is registered on every command but missing from the hand-written `--help`
- Severity: LOW
- Confidence: HIGH
- Location: cmd/shisa-de/main.go:221-223, cmd/shisa-de/flags.go:151-166
- Problem: `parse` registers `--compound`/`--no-compound` with the help text "the flag is accepted and refused", but `commonFlags` never lists it, so `shisa-de <command> --help` describes a flag set that silently omits a flag the parser accepts. The comment on `commonFlags` claims the help "cannot describe a flag that is not there"; here a flag that is there is not described. A user who reads Python's help or README and tries `--compound` gets exit 2 with no hint from `--help` that the flag exists.
- Recommendation: Add a `--compound / --no-compound` line to `commonFlags` (with the accepted-and-refused note), or, if the intent was to hide it, make that explicit in the comment.

### LOW: A null logprob prints as `0.0000`, and the divergence from Python's TypeError is not in PORT.md
- Severity: LOW
- Confidence: HIGH
- Location: cmd/shisa-de/explain.go:192-226
- Problem: Python's `sorted(read.top_logprobs.items(), key=lambda kv: -kv[1])` raises `TypeError` on a null logprob, so the reference walkthrough crashes. Go deliberately sorts the null last — a better behavior — but the printed line uses `entry.logprob`, which is `0` for a null, so a server's null is displayed as `0.0000`: the highest value a logprob can be shown as, placed last only by the sort. A reader diffing against the server's raw response sees a number the server did not send. PORT.md does not record this difference either.
- Recommendation: Print something that is not a number for a null (Python's own spelling, `None`, fits the walkthrough's repr conventions), and record the null-handling difference in PORT.md alongside the other `explain` differences.

### LOW: Two comments describe behavior the code does not have
- Severity: LOW
- Confidence: HIGH
- Location: cmd/shisa-de/doctor.go:78-96, cmd/shisa-de/state.go:9-14
- Problem: `orderedSlots`'s comment says "the count comes first and the codes follow in codebook order", but the code sorts the codes (`sort.Strings(codes)`). The output matches Python today only because the codebook's first two entries are `A` and `B`, so codebook order and sorted order coincide; if the codebook's first two codes ever differed from sorted order, `doctor --json` would silently diverge from the Python report. Separately, the const block in `state.go` is documented as "`defaultState` is the built-in example", but no identifier named `defaultState` exists.
- Recommendation: Either iterate the codes in codebook order (which is what the comment promises and what Python's `{**{...}}` produces) or fix the comment to say "sorted", and drop or rename the `defaultState` comment.

### LOW: Three output paths the reference defines have no test
- Severity: LOW
- Confidence: MEDIUM
- Location: cmd/shisa-de/main_test.go (file-wide)
- Problem: The tests cover the success paths and the boundary failure thoroughly, but: (1) nothing pins `doctor` exiting 1 when the report is not ok (an unlisted model, a failed boundary check, or a failed probe — the exit contract `README.md` advertises); (2) nothing pins `ask` exiting 1 with the error on stderr when the classify fails (a stub that returns a 500); (3) nothing pins `--state ''` producing an empty-text state rather than the built-in example, which is exactly the distinction `optionalStringValue` exists to make and which the scope calls out.
- Recommendation: Add the three cases; the stub server already supports all of them (an empty `models` list, an erroring completion handler, and `--state ''` against `stateFrom`).

## Things Checked

- **doctor**: text layout against `cli.py`'s print sequence line for line (alignment, the `NO` vs level rule, `True`/`False`, the conditional lines); `--json` against `json.dumps(report, indent=2)` including `reportOrder` vs Python's `health` key insertion order (matches, including `family_note` after `ok` and the mismatch/note exclusivity); `orderedSlots` vs `{"count": ..., **{...}}`; exit 0/1 vs `report["ok"]`; the absent `chat system` line is the documented difference.
- **ask**: head/labels shape vs `_labels_from` (including the `--prompt` wrapping), `Decision.Values` vs `dict(result)`, `indent=2, ensure_ascii=False`, exit statuses (2 usage, 1 classify failure), the map-order difference for `--confidence` being the documented one.
- **explain**: all five sections against `_explain`'s DE-2 branch — headings, the 72-char rule, slot lines, `sampled!r` via `PythonRepr`, the marks map, `%18s`/`%9.4f`/`%7.4f` formatting, the fallback line, the curl body's key order and `ensure_ascii=True`, `shlex.quote` (safe set matches `[a-zA-Z0-9_] + _@%+=:,./-`, empty string, embedded quote), `_api_key_from_env` (same two variables, same strip), the gate line and the option-cap check (26), and the direct-policy variants.
- **bestCode / sortedTopLogprobs**: tie-break against `max(probabilities, key=...)` given that both `read_codes` implementations reorder logprobs into slot order before softmax; the missing-code rule; the null ordering and its documentation status; block-merged top-logprobs (both merge per-block debug top-k the same way).
- **stateFrom / labelsFrom**: all three `--state` readings, `DecodeJSON` for int-vs-float preservation, the built-in example's key order (pinned by `TestStateAndLabels`), the default question, and the no-description → label rendering rule reaching the walkthrough identically to Python's `RenderOption`.
- **pyjson.go**: `appendPythonItemSeparator`/`appendPythonIndent` against CPython's separator switch, empty containers inline, `indent=""` vs nil, `: ` key separator, `ensure_ascii` code point ranges (DEL, C1, BMP, astral surrogate pairs), the fixture generator (22 values × 6 indents × 2 = 264 cases, values encoded `ensure_ascii=False` for `DecodeJSON`), the sha256/count/provenance checks in the test, and the negative comparator.
- **Exports**: `PythonRepr`/`PythonStr` doc comments and their CLI call sites (`sampled`, `InputRepeat`, option descriptions); `Readout.MaxLogprobs()` resolution vs `max_logprobs`; `PythonJSONWith` zero value = `ensure_ascii=False`.
- **.gitignore**: `/shisa-de` anchoring verified against the git index (all seven `cmd/shisa-de` files, the generator script and both fixture files are tracked); a sweep for files matching the remaining patterns found nothing silently ignored.
- **Tests**: the `newModel` seam (acceptable: single-goroutine use, restored via `t.Cleanup`, and `modelConfig` is still what the mapping tests exercise); the stub tokenizer/server design; the request-count assertions.
- **Docs**: `PORT.md`'s three command-line differences and the M5 status; `README.md`'s command-line section (accurate, including the `--model` default rationale).

## Residual Risks

- I had no shell tool in this session, so I could not run `git status`/`git diff` or the test suite; tracking status was verified by reading the git index directly, and the validation claims in the scope (gofmt, vet, tests, the live diffs) are taken as reported, not re-run.
- The fixture was generated on CPython 3.14.6; a regeneration on a different interpreter or Unicode version could legitimately change expected outputs for the non-ASCII cases, and the meta file records the interpreter so such a diff would at least be visible.
- The live-endpoint diffs are not re-runnable at test time (PORT.md says so); changes to the walkthrough layout would regress silently against the served model until the next manual diff.
- `--probabilities` on `ask` inherits the documented map-order rule (labels sorted rather than in option order); this is covered by PORT.md's general map-order paragraph but not called out for the distribution specifically.
- The `--timeout` edge values are untested on both sides: Go silently substitutes the library default for a zero or negative value, where a negative timeout is a construction error in the Python client.

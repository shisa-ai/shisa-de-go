# Review Report

## Summary

The M5 command line is a close port of `shisa_de/cli.py`. I checked the three commands line by line against the reference and could not find a wrong answer, a wrong exit status on the paths that are reachable, or a stream mix-up: `doctor`'s text lines and key order, `doctor --json`, `ask`'s JSON, and `explain`'s five sections, its top-k ordering, its `shlex.quote`d `curl` line and its footer all reproduce the Python command line's bytes on the paths the scope says were diffed. `PythonJSONWith`'s `indent`/`ensure_ascii` matches CPython's encoder on every point the scope lists (item separator, inline empty containers, `indent=""` vs `None`, DEL and the C1 block, astral surrogate pairs), and the 264-case fixture is a real oracle: it is generated by CPython 3.14.6, hashed in a provenance file, and accompanied by a negative test that proves Go's own indented encoder does not produce the same bytes. The flag layer's `optionalBool`/`optionalFloat`/`optionalInt`/`optionalStringValue` shapes are the right way to express what `argparse` distinguishes and Go's `flag` does not, and `bestCode` and `sortedTopLogprobs` are faithful to `max(..., key=...)` and the `-kv[1]` sort apart from two documented cases.

The findings are output-fidelity and validation edges, not wrong answers. The one that matters most: three message builders spell model and family names with Go's `%q`, where the Python client uses `!r`, so `doctor`'s `note` line and its calibration-reason lines differ from the Python command line on ordinary exit-0 runs — the runs `docs/PORT.md` claims are identical.

## Findings

### MEDIUM: `doctor` quotes model and family names with `%q` where Python uses `!r`
- Severity: MEDIUM
- Confidence: HIGH
- Location: client.go:768-770 (`family_note`), calibration.go:249,253,273 (`Applicability` reasons), printed at cmd/shisa-de/doctor.go:118-131 and in `doctor --json` via `orderedReport`
- Problem: the Python command line interpolates these strings with `!r`, which is single-quoted; this port interpolates them with `%q`, which is double-quoted. Two reachable, exit-0 paths differ:
  - an assumed family: Python prints `'my-adapter' carries no DE-1 or DE-2 slug; 'de2' was assumed, not detected`, this port prints `"my-adapter" carries ...; "de2" was assumed, not detected`;
  - a same-family record: Python prints `fitted on 'shisa-ai/shisa-de-2', not on 'shisa-ai/shisa-de-2-preview': same family, another checkpoint`, this port prints the same sentence with `"` instead of `'`.

  Both reach the text report (`note            ...`, and the indented reason lines under `calibration`) and `doctor --json`. `docs/PORT.md:563-566` says the text report and `--json` were compared line for line and are "identical apart from the numbers a fresh request changes and the one `chat system` line". That holds only for the run that was measured (`--model shisa-ai/shisa-de-2`, which resolves by slug so there is no `family_note`, and whose record matches the checkpoint so there are no reasons). `TestDoctorText` already exercises the reason case (`shisa-ai/shisa-de-2-preview`) but asserts only `strings.Contains(stdout, "same family, another checkpoint")`, so the quoting is not pinned. `client.go:599` has the same `%q`-for-`!r` substitution in the `Warnings` text; it is not printed, so it does not reach the command line.
- Recommendation: build these three reason strings and `family_note` with `pythonQuote` (the package's own `repr` for a string, which is what `!r` is) instead of `%q`, and add the exact expected lines to `TestDoctorText` so the parity claim is testable. Alternatively, if the double quotes are deliberate, record it in `docs/PORT.md` and narrow the parity claim to the measured run.

### LOW: `explain` prints the think gate with `%v`, so an integral gate prints `1`, not `1.0`
- Severity: LOW
- Confidence: HIGH
- Location: cmd/shisa-de/explain.go:173
- Problem: Python's f-string `{model.think_gate}` is `str(float)`, which is the float repr; `%v` is Go's shortest form. The default 0.7 prints identically in both, so the measured diff could not see it, but `explain --reasoning-prob 1` (a legal value: `ResolveOptions` accepts 0.0-1.0) prints `against the gate 1` here and `against the gate 1.0` in Python. The same pattern is in the `--reasoning-prob` help default in flags.go, where the default 0.7 hides it.
- Recommendation: print `shisade.PythonStr(model.ThinkGate())` (which routes through `pythonFloatString`/`appendPythonFloat`), and use the same spelling in the help text.

### LOW: an explicitly empty `--family`, `--policy`, `--reads` or `--calibration` is read as "not given"
- Severity: LOW
- Confidence: HIGH
- Location: cmd/shisa-de/main.go:141,148,162,171
- Problem: `argparse` validates `choices` at parse time, so `--policy ''`, `--reads ''` and `--family ''` are invalid choices and exit 2, and `resolve_calibration("")` reaches `load_calibration_file("")`, whose `Path("")` is not a file, so Python exits 2 with `--calibration '' is neither a family (de1, de2) nor a record file`. This port tests `!= ""` and silently falls back to the default read and the bundled record, so a wrapper that passes `--policy "$POLICY"` with `POLICY` unset gets the default instead of an error. The `--state` flag shows the intended treatment (`optionalStringValue` distinguishes absent from empty, main.go:210-213) but the four choice flags do not get it. Two smaller leniencies are in the same class: `--family DE-2` is accepted (`NormalizeFamily` normalizes; `argparse` rejects anything but `de1`/`de2`), `--reasoning=false` is accepted (`BoolFunc` takes an explicit value; `BooleanOptionalAction` has `nargs=0` and errors), and `shisa-de help` prints the top usage and exits 0 where `argparse` treats `help` as an unknown command and exits 2. `--timeout 0` is also silently 120s here (readout.go's documented zero-value rule) where Python passes 0 to `httpx`.
- Recommendation: record set-from-empty for `--family`, `--policy`, `--reads` and `--calibration` the way `--state` does (an `optionalStringValue` plus an explicit emptiness check that reports a usage error), or add one `docs/PORT.md` paragraph saying the port is deliberately more permissive on these, since "a difference that is not in it is an accident" per AGENTS.md.

### LOW: `stateFrom` and `labelsFrom` trim with Go's whitespace set, not Python's
- Severity: LOW
- Confidence: HIGH
- Location: cmd/shisa-de/state.go:43,63; same helper at explain.go:257
- Problem: Python's `_state_from` uses `text.strip()` and `_labels_from` uses `part.strip()`, which strip U+001C-U+001F; `strings.TrimSpace` does not (the package's own `TestPythonSpaceIsPythonsStrip` pins exactly this, and `questions.go:46-53` has `isPythonSpace`/`trimPythonSpace` for it). So `--state $'\x1c{"a": 1}'` parses as JSON in Python and is passed through as plain text here, which is a different prompt and a different answer. `apiKeyFromEnv` (explain.go:257) has the same substitution, where the only visible effect is printing the `Authorization` line for an env var that is exactly a U+001C separator.
- Recommendation: use the Python whitespace set in `cmd/shisa-de` — export `TrimPythonSpace` (or a small `pythonSpace` helper) from the library, since the CLI cannot reach the unexported one.

### LOW: `reportOrder` silently drops any report key it does not know, and nothing ties it to `Health`
- Severity: LOW
- Confidence: HIGH
- Location: cmd/shisa-de/doctor.go:49-79
- Problem: `orderedReport` iterates the hardcoded `reportOrder` and skips keys the report does not carry, so a key added to `Health` and forgotten here vanishes from `doctor --json` while the text form (which names its keys individually) may still print it, and the two forms would disagree. `TestDoctorJSON` checks nine keys are present, not that the key sets agree. This is the one place the port trades Python's "print everything" for a hand-maintained list, and `docs/PORT.md:285-286` justifies it on the grounds that "the report's key set is fixed and the command line knows it" — which is true only as long as someone remembers.
- Recommendation: add a test that walks `Health`'s map for a stubbed model and fails if any key is missing from `reportOrder` (the reverse direction, `chat_system_render`, is already impossible here), so the coupling is enforced rather than asserted.

### LOW: `explain` takes the read before printing anything, which is not Python's order, and the test comment says it is
- Severity: LOW
- Confidence: HIGH
- Location: cmd/shisa-de/explain.go:62-88; main_test.go:800-810
- Problem: Python's `_explain` prints sections 1 and 2 and only then calls `readout.read_codes`, so a read failure leaves two sections on stdout before the traceback; this port renders, checks the boundary, takes the read, and only then prints, so a read failure prints nothing. That is a defensible improvement (and `TestExplainReportsAnUnreadableQuestion` proves the *boundary-check* failure prints nothing, which is true in Python too), but the difference is not in `docs/PORT.md`, and the test's comment — "The walkthrough takes the read before its first line, which is the Python command line's order" — is wrong about Python for a read failure.
- Recommendation: fix the comment to say the ordering is this port's choice, and add the one-line difference to `docs/PORT.md` (the failure mode is observable: exit 1 with empty stdout here, exit 1 with sections 1-2 on stdout there).

### LOW: nothing tests `doctor`'s non-zero exit for a report that is not ok
- Severity: LOW
- Confidence: HIGH
- Location: cmd/shisa-de/doctor.go:29-46; cmd/shisa-de/main_test.go (no case)
- Problem: `README.md:69-70` and the `doctor` contract both promise a non-zero exit when the report is not ok, and `runDoctor` implements it (`return 1` when `report["ok"]` is false, plus `return 1` when the report will not render). Every `doctor` test drives a passing report. A regression that returned 0 unconditionally would not be caught.
- Recommendation: add one case with a stub whose `/v1/models` omits the served id (or whose tokenizer breaks the boundary check) and assert status 1 and a report whose `ok` is `False`.

### LOW: `stateFrom`'s error return is always nil, so two exit-2 branches are dead
- Severity: LOW
- Confidence: HIGH
- Location: cmd/shisa-de/state.go:31-56; cmd/shisa-de/ask.go:20-23; cmd/shisa-de/explain.go:29-32
- Problem: `stateFrom` returns `(any, error)` and never produces an error: a `{`-prefixed string that does not parse is the state, which is what `json.JSONDecodeError` gives Python. The `return 2` paths in `ask` and `explain` therefore cannot run, and if a real error is ever added the exit status chosen for it (2, a usage error) may not be the right one.
- Recommendation: drop the error return and let the callers take the value, or keep it and add the case that produces it so the status is exercised.

## Things Checked

- **`doctor` text layout and order.** Compared `writeDoctorReport` against `cli.py`'s f-strings line by line: labels, padding, the `NO`/`yes`/`no` spellings, the conditional `model listed` line (`served_models is not None` becomes a `[]string` type assertion, and `Health` only sets the key on a successful listing, so the empty-list case cannot diverge), the `read probe` line, and `ok` printed as Python's `True`/`False` via `pythonBool`. The report key order in `reportOrder` matches `client.py:456-519`'s insertion order exactly, including the position of the conditional `family_note`, `calibration_match`, `calibration_mismatch`/`calibration_note` and `read_probe`; `slots` is `{"count": ..., first two codes}` in both, and `orderedSlots`' sort agrees with the codebook's order for the first two codes.
- **`doctor --json`.** `PythonJSONWith(orderedReport(report), {Indent: "  ", EnsureASCII: true})` is `json.dumps(report, indent=2)` (which does not pass `ensure_ascii`, so it defaults true); `ask`'s `Indent` with `EnsureASCII` left false is `json.dumps(..., indent=2, ensure_ascii=False)`. Both add one trailing newline via `Fprintln`, matching `print`.
- **`ask`.** `Decision.Values` under `PythonJSONWith` is `dict(result)`; `--confidence`/`--probabilities` produce the same value shapes as `Classify` in `client.py` (`label`, `confidence`, `probabilities`, plus `strategy`/`score_semantics`/`calibrated` when the semantics are not `option-softmax`), with the documented sorted-key difference. `--prompt` sets `HeadSpec.Instructions`, and an absent one falls through to `defaultQuestion("intent")`, which is `_labels_from` + `_default_question`.
- **`explain`.** All five headings, the 72-dash rule, the slot table (`%6d` vs `{token_id:>6}`), the request line, `prompt tokens/requests/sampled` (`reprOptionalString` gives `None` for a missing `text`), the `marks` map over both the code and `token_id:<id>`, `{token!r:>18}` vs `%18s` + `PythonRepr`, `{logprob:9.4f}` vs `%9.4f`, the fallback line, the distribution line with `str(description)` (Python's `render_option` substitutes the key for a blank description, and `NewChoice` does the same, so both print `(order_status)` rather than `(None)`), the answer line, the `curl` body key order (`model, prompt, max_tokens, temperature, logprobs, return_tokens_as_token_ids, logprob_token_ids`) and its `ensure_ascii=True`, and the footer's three conditional lines.
- **`bestCode`.** Python's `answer()` is `max(probabilities, key=probabilities.get)` over a dict built in slot order, so it is the lowest-index slot on a tie; `bestCode` iterates the slots in order with a strict `>`, so it is the same choice, skips a code the read did not return (Python's `max` only sees the dict's own keys), and treats a missing distribution as an error where Python raises `ValueError` on `max(())`. The test pins the tie and the zero-probability cases.
- **`sortedTopLogprobs`.** Descending by logprob, which is Python's `key=lambda kv: -kv[1]`; a null sorts last where Python raises `TypeError` (documented in the function), and a tie breaks on the token where Python keeps the server's order (documented in the function, not in PORT.md — no output change unless a server returns exactly equal logprobs).
- **`shlexQuote`.** Same safe set as `shlex.quote` (`\w` under `re.ASCII`, plus `@%+=:,./-`), same `''` for empty, same `'"'"'` closing for an embedded quote, and the same literal-newline passthrough. The tests cover the empty, safe, quoted, `$`, JSON and newline cases.
- **`stateFrom` / `labelsFrom` / `defaultQuestion`.** The three `--state` readings (absent → built-in, `{`/`[` → `DecodeJSON` so `3` stays `3`, malformed `{` → the text itself) match `_state_from`; the built-in state is a `shisade.Object` with `ticket` before `account`, which is Python's dict order and reaches the prompt; `labelsFrom` drops blank parts and defaults to the four labels; `defaultQuestion` matches `head.replace("_", " ")`. The only divergence is the whitespace set (finding above).
- **Flag parsing.** The `--no-` forms share one value and leave the other flag nil, so the library's defaults still apply; a bare `--reasoning`/`--no-reasoning` is a `BoolFunc` with no separate argument, matching `BooleanOptionalAction`; `--reasoning-prob`/`--reasoning-len` map to `ReasoningProb`/`ReasoningLen` (the aliased names), not to `ThinkGate`/`ThinkBudget`; `--family` goes through `NormalizeFamily`, `--calibration` through `ResolveCalibration` (whose `""`/`"auto"` handling matches `resolve_calibration`), and `--policy`/`--reads` are checked against the same lists as `POLICIES`/`READS`. Bad flags, missing values, unknown commands and a leftover positional all exit 2 with the usage on stderr and nothing on stdout; `-h`/`--help`/`<cmd> --help` exit 0 with the usage on stdout.
- **`PythonJSONWith` semantics.** Read against CPython's encoder: `(',', ': ')` compact and `(',', ': ')` with the newline coming from the indent when indenting; `{}`/`[]` inline; `indent=""` distinct from `indent=nil` via the pointer; DEL and the C1 block escaped under `ensure_ascii` (the encoder's `[^\x20-\x7e]`); `\x00`-`\x1f` escaped with the four short forms; astral code points as UTF-16 surrogate pairs; no escaping of `<`, `>`, `&`, `/` or U+2028/U+2029. The fixture crosses 22 values with `None, "", 0, 1, 2, 4` and both `ensure_ascii` settings, is generated by CPython 3.14.6, is sha256-pinned in `pyjson_dumps.meta.json`, and `TestPythonJSONIndentIsNotGoIndent` fails if Go's own encoder ever produces the same bytes, so the fixture cannot pass by accident. Gaps: no non-space `indent` string, and the map-key-sorting path is covered by a unit test rather than the fixture.
- **The new exports.** `PythonJSONWith`/`PythonJSONOptions` are the `json.dumps` keyword arguments the CLI actually needs; `PythonStr`/`PythonRepr` are pure functions the CLI cannot reimplement faithfully (the `repr` table is generated); `Readout.MaxLogprobs` is a read-only accessor over a configured field. None exposes mutable internals, and `AGENTS.md` already records that `cmd/shisa-de` is the second consumer that has to be kept in step.
- **`.gitignore`.** The rule is now `/shisa-de`, anchored, so `cmd/shisa-de/` is no longer matched; `/bin/`, `/tmp/`, `*.exe`, `*.test`, `*.out` remain. `tokenizer.json` stays deliberately unanchored: `tokenizer/hub.go:88-92` looks for `testdata/tokenizer.json` and `tokenizer/testdata/tokenizer.json`, so anchoring it would start tracking the 32 MB download. I found no other file in the tree that the current rules silently ignore (no `*.out`, `*.test`, `*.exe` or stray `tokenizer.json` exists), and the test seam file `cmd/shisa-de/main_test.go` is tracked.
- **`newModel` as a seam.** A package-level `var newModel = shisade.NewDecisionModel` replaced by `installCLIModel` and restored in `t.Cleanup` is the standard Go way to inject a constructor, it is documented as a test seam, the flags still go through `modelConfig` (so the mapping tests are not bypassed), and no test in the package calls `t.Parallel()`. Acceptable as written; the caveat is in Residual Risks.
- **`TestExplainReportsAnUnreadableQuestion`.** The stub tokenizer is swapped to one with an empty word list before `invoke`, so `AnswerPrefixID` refuses `<channel|>`, `CheckCodeBoundary` fails, and the test asserts status 1, empty stdout and zero requests. That does prove the boundary-check failure precedes every print. It does not exercise a *read* failure, which is where the Python ordering differs (finding above).
- **Docs.** `README.md`'s command-line section, `AGENTS.md`'s key-file table and `docs/PORT.md`'s five command-line paragraphs match the code; the `--model` default, the absent image flags, the absent DE-1 branch and the absent `chat system` line are all real and all recorded. The parity claim in "Verified parity" is narrower than its wording (finding above). The `--help` text is this port's own layout, not `argparse`'s (no `usage: ... [-h]`, no metavars, no positional section); that is not recorded in PORT.md either, but the reference help text is not part of what the scope asks the port to reproduce.

## Residual Risks

- The parity evidence for the command line is one manual diff against the hosted endpoint, not a fixture, and it is not re-run at test time. It therefore pins the *passing* paths of the two models that were tried, not the output of an assumed family, an uncovered checkpoint, a failing boundary check or an error message; the MEDIUM finding lives in exactly that gap.
- The command-line tests use a stub tokenizer whose word list is invented for the test, so they pin the port's own control flow and text layout, not the bytes a real tokenizer produces. `explain`'s prompt, slot ids and token counts are therefore not gated by anything here (the render and readout fixtures cover those layers).
- `reportOrder` is a second, hand-maintained copy of `Health`'s key set; nothing enforces the coupling until the test recommended above exists.
- `newModel` is process-global and mutable. A `t.Parallel()` added to any test in `cmd/shisa-de` would race with `installCLIModel`, and any future in-process second caller of `run` would share it.
- `sortedTopLogprobs`' tie-break (token order) and its null handling are documented in the function but not in `docs/PORT.md`, which the repo's own rule says is where deliberate differences belong. Neither is reachable without a server returning equal logprobs or a null.
- `--timeout 0` and `--reasoning-prob` values that are integral floats are two more places where the port's zero-value/`%v` conventions and Python's differ; I verified the code paths but could not run the Python command line to confirm what `httpx` does with a zero timeout.

# Review Report

## Summary

The M1 tokenizer is careful work and the core of it is right. I read the pinned `tokenizer.json` from the local hub cache (snapshot `8f21734b27b3462471c4662d5638e52195b005a3`, whose `refs/main` matches the pin) and confirmed the stages the package hardcodes are exactly the stages that file declares: normalizer `Replace " " -> "▁"`, pre-tokenizer `Split " "` `MergedWithPrevious` `invert:false`, decoder `Sequence[Replace, ByteFallback, Fuse]`, `post_processor` `TemplateProcessing` with an empty `special_tokens` map, and a BPE model with `byte_fallback:true`, `fuse_unk:true`, `ignore_merges:false`, 24 added tokens and 514,906 merges. So the fidelity claim holds for the pinned file, and the parity run is against a file whose shape matches what the code assumes.

The heap merge in `bpe.go` is correct, and I could not construct a case where a stale candidate merges a pair that is no longer adjacent or whose symbols have changed. The guard is sound and the argument is stronger than the code comment gives it credit for (details under Things Checked).

The risk is not in the merge. It is in the promise that the package "rejects rather than approximates". Two pipeline stages are hardcoded instead of driven by the parsed file, the `decoder` section is never parsed at all, and the hub layer can silently return a different revision than the caller pinned or cache a bad download permanently. Separately, the parity gate that is supposed to catch all of this can skip in CI, and nothing pins the corpus or the tokenizer's identity, so the gate can weaken without anyone noticing. Those are the findings below; there is no CRITICAL or HIGH.

## Findings

### MEDIUM: Pipeline stages are hardcoded, so shapes the package promises to reject are silently approximated
- Severity: MEDIUM
- Confidence: HIGH
- Location: tokenizer/tokenizer.go:225-262 (`checkNormalizer`, `checkPreTokenizer`), tokenizer/tokenizer.go:348-350 (`normalize`), tokenizer/tokenizer.go:357-387 (`preTokenize`), tokenizer/tokenizer.go:61-68 (`tokenizerFile`), tokenizer/tokenizer.go:289-305 (`Decode`)
- Problem: the validators check the stage *type* and then the implementation ignores the stage *contents*, so a file the package claims to reject is read as if it were the pinned one. Concretely:
  - `normalize` unconditionally replaces `" "` with `"▁"`. `checkNormalizer` returns nil when there is no normalizer at all (`spec.Type == ""`), and accepts any literal `Pattern.String` and any `Content` (including `""`), and ignores `Invert`. A file with no normalizer, or `Replace "▁" -> " "`, or `Replace " " -> ""` is silently read with the pinned normalizer's behaviour. With no normalizer and the pinned `Split " "` pre-tokenizer, Hugging Face would split on spaces and byte-fallback each space to `<0x20>`, while this package produces `▁` symbols: different ids, no error.
  - `preTokenize` hardcodes `const pattern = " "`. `checkPreTokenizer` accepts any literal `Pattern.String`, and validates `Behavior` against four values (tokenizer.go:251-254) and then ignores it, always applying `MergedWithPrevious`. `Invert` is ignored. `Isolated`, `Removed` and `Contiguous` are explicitly allowed and then mis-implemented.
  - `tokenizerFile` has no `Decoder` field (tokenizer.go:61-68). `Decode` hardcodes `Replace("▁"->" ")` plus `<0xXX>` byte conversion, so a file whose decoder is `Strip`, `Metaspace`, `ByteLevel` or anything else is silently decoded with the pinned chain. `PostProcess` is parsed (tokenizer.go:67) and never inspected; that is harmless for this file (its template adds no tokens) but it is not the rejection the package doc promises.
  - The package doc comment (tokenizer.go:1-14) states that a file needing an unimplemented stage "is rejected rather than approximated". For the cases above it is approximated.
- Recommendation: compare the parsed spec against the expected values and return `*ErrUnsupported` when they differ — normalizer present with `Pattern.String == " "` and `Content == "▁"` and `Invert == false`; pre-tokenizer `Split` with `Pattern.String == " "` and `Behavior == "MergedWithPrevious"`; a `Decoder` field present and equal to the pinned `Sequence[Replace, ByteFallback, Fuse]`. Driving the two stages from the parsed `stageSpec` instead of constants would also work and is less code, but then the type check must stay strict. Either way, add one rejection test per shape (no normalizer, wrong normalizer content, `Split` with `Behavior: "Isolated"`, a `Strip` decoder).

### MEDIUM: `Lookup`'s any-snapshot fallback defeats an explicit pin, and nothing downstream can tell
- Severity: MEDIUM
- Confidence: HIGH
- Location: tokenizer/hub.go:176-181 (fallback), tokenizer/hub.go:42-55 (`Resolve`), tokenizer/tokenizer_test.go:30-34 (`loadPinned`), render_test.go:284-289
- Problem: when the caller asks for a snapshot hash that is not in the local cache, `Lookup` falls through to `filepath.Glob(.../snapshots/*/tokenizer.json)` and returns `matches[0]` from any revision. `Resolve` returns that path as if it satisfied the request, and `Load` gives the caller no way to see which revision it got. The parity test is affected: `loadPinned` calls `Lookup(pinnedRepo, pinnedSnapshot)` and treats the result as the pinned tokenizer, so a machine that has a different snapshot cached but not `8f21734b...` will run the whole parity gate against the wrong file and report it as parity for the pin. The same applies to `Lookup(pinnedRepo, "main")` when `refs/main` is missing. Nothing downstream catches this: the caller cannot observe the revision, and the test only fails if the ids happen to differ.
- Recommendation: when `revision` is a snapshot hash (`isSnapshot`), do not fall back to another snapshot — return false so `Fetch` runs, or fail with an error naming the missing revision. If the fallback is kept for the branch-name case, return the resolved revision (e.g. `Lookup(repo, revision) (path, resolved string, ok bool)`) so `Load` can log or verify it. In `loadPinned`, assert the loaded tokenizer's identity (see the next finding) rather than trusting the path.

### MEDIUM: `Fetch` installs an unvalidated body and treats any non-empty cache file as a good one
- Severity: MEDIUM
- Confidence: HIGH
- Location: tokenizer/hub.go:75-79 (cache check), tokenizer/hub.go:100-120 (write and rename), tokenizer/hub.go:200-203 (`exists`)
- Problem: the response is streamed to a temp file and renamed into the cache with no check that it is a tokenizer at all. Any body returned with a status below 400 is installed — an HTML interstitial from a proxy or CDN, a JSON error object, or a transfer that ends early on a chunked response (which `io.Copy` reports as a clean EOF). After that, the cache-hit path at hub.go:76 accepts any file with `Size() > 0`, so the poisoned file is returned on every later call and `FromFile` fails with a JSON parse error until someone deletes the cache entry by hand. The same weak test is used by `exists` (hub.go:200) and therefore by `Lookup`, so a stale or truncated file in the Hugging Face cache is preferred over downloading a good one. The temp-file-and-rename itself is fine: a concurrent reader never sees a half-written file, and two concurrent `Fetch` calls both rename atomically.
- Recommendation: before `os.Rename`, validate the temp file — at minimum `json.Unmarshal` into `tokenizerFile` and check `model.type == "BPE"` and a non-empty vocab (i.e. reuse `FromBytes`), and delete it otherwise. On the cache-hit path, treat a file that `FromFile` rejects as absent and re-fetch. A `Content-Length`/size sanity bound (the pinned file is ~32 MB) would also catch HTML pages early.

### MEDIUM: The parity gate skips silently and pins neither the corpus nor the tokenizer's identity
- Severity: MEDIUM
- Confidence: HIGH
- Location: tokenizer/tokenizer_test.go:23-54 (`loadPinned`), tokenizer/tokenizer_test.go:56-105 (`TestParityVectors`)
- Problem: with no `tokenizer.json` on the machine, all four tokenizer tests call `t.Skipf` and `go test ./...` exits 0. The 32 MB file is deliberately not checked in, so on a clean CI runner the tokenizer package contributes zero verification while the suite reports success. `go test` prints `SKIP`, but an exit-code gate cannot distinguish that from a pass; the AGENTS.md note "a parity test that has no vectors is a skip, not a pass" documents the intent but nothing enforces it. The corpus is unpinned too: `TestParityVectors` only requires `len(vectors) != 0`, so `docs/PORT.md`'s "1,051 strings, 48,296 token ids" is not checked by anything, and a regenerated fixture with a fraction of the inputs would pass. The loaded tokenizer's identity is never checked either: `loadPinned` accepts whatever `FromFile` parses, so a stale `testdata/tokenizer.json` or a hub-cache fallback (previous finding) is used as "the pinned tokenizer" and produces confusing id mismatches instead of a clear error.
- Recommendation: keep the skip for a developer machine, but add a strict mode (`SHISA_DE_TOKENIZER_REQUIRE=1` makes `loadPinned` fail instead of skipping) and use it in CI, or have CI assert that the parity test ran. Inside `loadPinned`, assert the loaded tokenizer is the pinned one (`Len() == 262144`, `TokenID("<channel|>") == 101`, and the merge count if it is exposed) and `t.Fatalf` with the path and the mismatch otherwise. In `TestParityVectors`, assert the expected vector and id counts so a shrunk corpus is a failure rather than a smaller green run.

### MEDIUM: The vector generator does not pin the revision, records no provenance, and drops corpus inputs it cannot find
- Severity: MEDIUM
- Confidence: HIGH
- Location: scripts/gen_tokenizer_parity.py:12-15 (docstring), scripts/gen_tokenizer_parity.py:180 (`AutoTokenizer.from_pretrained(MODEL)`), scripts/gen_tokenizer_parity.py:148-160 (repository text inputs), scripts/gen_tokenizer_parity.py:184-193 (output)
- Problem: the docstring states the vectors come from snapshot `8f21734b...`, but `from_pretrained(MODEL)` passes no `revision`, so it resolves `main` at generation time. It happens to be the same commit right now (the local `refs/main` is `8f21734b...`), so today's vectors are consistent with the pin; the next regeneration after an upstream commit silently produces vectors from a different revision while the test, the docstring and `docs/PORT.md` still claim the snapshot. Second, the corpus reads three files from a hardcoded machine-local checkout, `pathlib.Path.home()/"data"/"dev"/"shisa"/"shisa-de"` (line ~57), guarded by `if path.exists()` with no warning, so on any other machine roughly 30 vectors vanish without notice. Third, the output is a bare list of `{text, ids}` pairs: no model id, no revision, no `tokenizers`/`transformers` version, so the vectors cannot be re-attributed later — which the repository's own evidence rules require of any recorded number. The parity test cannot detect any of this (previous finding).
- Recommendation: pass `revision="8f21734b27b3462471c4662d5638e52195b005a3"` to `from_pretrained`, take the Python repository path from a flag or environment variable and fail loudly when a corpus input is missing (or record in the output which inputs were used), and write the provenance beside the vectors — either a header object in the JSON or a sibling `testdata/tokenizer_parity.meta.json` holding the model, revision, library versions, string count and id count.

### LOW: `byID` is filled by map iteration, so duplicate or negative vocab ids are nondeterministic or silently accepted
- Severity: LOW
- Confidence: HIGH
- Location: tokenizer/tokenizer.go:159-175
- Problem: `for token, id := range t.vocab { if id >= 0 { t.byID[id] = token } }` iterates a Go map, so if two tokens share an id the winner changes from run to run and `Decode` is nondeterministic. Hugging Face builds `id_to_token` deterministically from the file. Negative ids are skipped for `byID` but remain in `t.vocab`, so `Encode` can return a negative id that `Decode` then drops; a JSON id that cannot fit `int32` is a parse error in Hugging Face but is silently ignored here.
- Recommendation: detect duplicate and negative ids while filling `byID` and return `*ErrUnsupported` (or an error naming the id) rather than accepting the file.

### LOW: An out-of-range vocab id sizes the `byID` allocation
- Severity: LOW
- Confidence: HIGH
- Location: tokenizer/tokenizer.go:159-170
- Problem: `maxID` is the largest id anywhere in `vocab` or `added_tokens`, and `t.byID = make([]string, maxID+1)`. A single entry with an id near `math.MaxInt32` (which unmarshals fine into `int32`) asks for a 16 GB slice; `FromFile` is reachable from a downloaded file via `Load`, so a malformed or hostile `tokenizer.json` is an out-of-memory kill rather than an error. The only structural check is that the vocab is non-empty (tokenizer.go:130-132).
- Recommendation: bound the id before allocating (for example, reject any id greater than the number of vocab entries plus added tokens, or a fixed ceiling) and report it as unsupported.

### LOW: `Fetch`'s destination and URL are built from unescaped caller strings, and the download has no size cap
- Severity: LOW
- Confidence: MEDIUM
- Location: tokenizer/hub.go:75, tokenizer/hub.go:82
- Problem: `filepath.Join(cacheDir(), filepath.FromSlash(repo), revision, "tokenizer.json")` cleans `..` segments, so a `repo` or `revision` containing traversal escapes the cache directory and the downloaded body is written to the resulting path. Reaching the write requires a 2xx response, and the URL is built with the same unescaped strings, which limits exploitability, but the write path is not confined to the cache as intended. `revision` is also placed in the URL unescaped, so `?` or `#` changes the request's meaning. There is no cap on the response body, only the client's 10-minute timeout.
- Recommendation: validate the source shape before use — `repo` as `owner/name` with no `.`/`..` segment and no separator, `revision` as a plain ref or hash — and reject anything else. Use `url.PathEscape` for both when formatting the URL, and cap the copy with an `io.LimitReader`.

### LOW: `cacheDir` can fall back to a shared temporary directory
- Severity: LOW
- Confidence: MEDIUM
- Location: tokenizer/hub.go:123-133
- Problem: when `os.UserCacheDir` fails, the cache becomes `os.TempDir()/shisa-de/tokenizer`, created `0755` under a shared `/tmp`. On a multi-user machine another user can create that path first and own the directory the process then writes a downloaded file into.
- Recommendation: fail with an error instead of falling back to `os.TempDir()`, or create the fallback directory with `0700` and verify its ownership before using it. Prefer requiring `SHISA_DE_TOKENIZER_CACHE` in that situation.

### LOW: `Decode`'s byte-fallback branch is untested, and it likely diverges from Hugging Face on invalid byte runs
- Severity: LOW
- Confidence: LOW for the divergence (Hugging Face's `ByteFallback` source is not on this machine and I could not verify it); HIGH for the coverage gap
- Location: tokenizer/tokenizer.go:289-305, tokenizer/tokenizer_test.go:139-146
- Problem: `TestDecode` round-trips eight short strings. Every character in them is a single vocab token — `"日"` is id 237205 and `"🙂"` is id 240731 in the pinned file — so no case produces a `<0xXX>` id and the `<0xXX>` branch of `Decode` (the only part that is more than a string replace) is never executed. Separately, `Decode` appends the raw byte for every `<0xXX>` token, whereas Hugging Face's `ByteFallback` decoder accumulates consecutive byte tokens and, on my recollection, emits the literal `<0xXX>` strings when the accumulated bytes are not valid UTF-8; for an isolated `<0xFF>` the two would return `"\xff"` and `"<0xFF>"` respectively. That is unreachable from `Encode` (byte-fallback tokens are only produced from valid UTF-8 characters) but it is reachable from hand-built id lists, which is how a caller checking a server's returned token ids would use `Decode`.
- Recommendation: add a decode case that exercises the branch — round-trip a string containing a character absent from the vocab (for example `"\u001b[31mred"`; I confirmed `\u001b` is not a single token in the pinned vocab) or decode a hand-built `<0xE6><0x97><0xA5>` id list. Then check the invalid-run case against `tokenizers` and either match it or document the difference at the function.

### LOW: The pin's provenance comment is wrong in two test files
- Severity: LOW
- Confidence: HIGH
- Location: tokenizer/tokenizer_test.go:13-16, render_test.go:14-16
- Problem: both files say the pinned checkpoint is "as recorded in data/codebook-de2.json" and then pin `shisa-ai/shisa-de-2` at `8f21734b27b3462471c4662d5638e52195b005a3`. That file records something else: `"tokenizer": "google/gemma-4-26B-A4B-it"`, `"tokenizer_snapshot": "4d7ae4984b7db7de8f8457170b3f1a419ee76d52"` (data/codebook-de2.json:3-4). The two are consistent in content for the codes — `TestParityCoversEveryCodebookCode` cross-checks the gemma-audited `token_ids` against the shisa tokenizer, which is a genuinely useful check — but the comment tells a maintainer the opposite of what the files say, and it is the kind of provenance claim this repository treats as load-bearing.
- Recommendation: state each pin's actual source. For example, in the tokenizer test: "the tokenizer the parity vectors were generated from (`scripts/gen_tokenizer_parity.py`, model `shisa-ai/shisa-de-2`, revision `8f21734b...`); the codebook's `token_ids` were audited on `google/gemma-4-26B-A4B-it@4d7ae498...`, and `TestParityCoversEveryCodebookCode` checks that the two agree."

### LOW: The pinned-tokenizer resolution is duplicated in three places and already differs
- Severity: LOW
- Confidence: HIGH
- Location: tokenizer/tokenizer_test.go:23-54 (`loadPinned`), tokenizer/tokenizer_test.go:260-279 (`loadPinnedBench`), render_test.go:276-300 (`pinnedTokenizer`)
- Problem: the same candidate order is written three times, in two packages. They have already drifted: `loadPinned` and `pinnedTokenizer` try `SHISA_DE_TOKENIZER_JSON` before the hub cache, `loadPinnedBench` tries the hub cache first, so a developer with both set gets a different tokenizer in the benchmark than in the parity test. `loadPinned` also silently ignores a `SHISA_DE_TOKENIZER_JSON` path that does not exist or has size 0 (`exists` at tokenizer_test.go:23-54 / hub.go:200), falling through to whatever the hub cache holds — a typo in the variable becomes a different tokenizer with no warning. `pinnedTokenizer` differs again by using `os.Stat` + `info.Size() == 0` instead of `exists`.
- Recommendation: one exported helper in the tokenizer package (for example `LoadPinned(repo, revision string) (*Tokenizer, string, error)`), used by all three, that reports which path and revision it used, fails on an explicitly set but unusable `SHISA_DE_TOKENIZER_JSON`, and is the single place the identity assertion from the earlier finding lives.

## Things Checked

- **The pinned file's declared pipeline.** Read from `~/.cache/huggingface/hub/models--shisa-ai--shisa-de-2/snapshots/8f21734b27b3462471c4662d5638e52195b005a3/tokenizer.json` (`refs/main` also resolves to `8f21734b...`): `normalizer` `Replace {"String":" "}` -> `"▁"`; `pre_tokenizer` `Split {"String":" "}` `MergedWithPrevious` `invert:false`; `post_processor` `TemplateProcessing` with `special_tokens: {}` and a single sequence; `decoder` `Sequence[Replace("▁"->" "), ByteFallback, Fuse]` (no `Strip`); `model` `BPE`, `unk_token "<unk>"`, `byte_fallback:true`, `fuse_unk:true`, `ignore_merges:false`; 24 `added_tokens`; `merges` as two-element string arrays. `tokenizer_config.json` has no `truncation`, no `padding` and no `added_tokens_decoder`, so reading only `tokenizer.json` is safe for this checkpoint.
- **`bpe.go` staleness guard.** `removed[l] || removed[r] || next[l] != r || symbols[l] != a || symbols[r] != b` catches every staleness I could construct: a merge at `r` changes `symbols[r]`; a merge at `prev[l]` removes `l`; a merge between `l` and `r` breaks `next[l] == r`. The stronger property also holds: because every newly adjacent pair is pushed (`pushPair` after each merge) and entries are only ever popped, every currently adjacent pair is represented in the heap at all times, so popping the minimum cannot skip a lower-ranked valid pair. A candidate that survives the guard is by construction the current pair at `(l, r)`, with the same rank and id, because `merges` is keyed by the symbol pair. The `(removed[l], next[l]==r, symbols==)` guard is therefore sufficient, and no case merges a pair that is no longer adjacent or whose symbols changed.
- **Tie-break observability.** `["x","x"]` is a real merge in the pinned file (tokenizer.json:396842-396844), and the fixture contains a run of at least 30 `x` (and `▁`*300, `ab`*200, `" "*200`, `"\n"`*30), so the leftmost-on-equal-rank rule is genuinely constrained by the parity run rather than assumed. My reading of Hugging Face's `Merge` ordering (rank, then position, lowest first) is from memory and is not verified here — see Residual Risks.
- **Pre-tokenizer split.** `preTokenize` returns `["a ", "b ", "c"]` for `"a b c"`, `[" ", "b"]` for `" b"`, and `["a ", " ", "b"]` for `"a  b"`, which is `MergedWithPrevious`. It is dead code for the pinned file because the normalizer removes every space first, as the scope states.
- **`Decode` against the pinned decoder.** Ordering is equivalent to Hugging Face's chain: testing the raw vocab token for the 6-character `<0xXX>` shape before replacing `▁` cannot disagree with replacing `▁` first, because that replacement cannot create or destroy a `<0xXX>` token, and `Fuse` only regroups the strings that `decode` finally joins with `""`. Lowercase hex is accepted by both.
- **Byte-fallback reachability of `unk`.** All 256 `<0xXX>` tokens exist in the pinned vocab (ids 238-493, checked at four points). Every character is therefore either a vocab token or byte-fallback-able, so `unk` cannot be produced by this tokenizer and `fuseUnknowns` is unreachable dead code that no corpus can test. `fuseUnknowns` itself is correct (fuses consecutive `unk`, writes over its own fresh slice, no aliasing of caller data).
- **Concurrency.** `Tokenizer` is read-only after `FromBytes`: `vocab`, `byID`, `merges`, `byteID`, `byteOK` and `added.byFirst` are never written by `Encode`/`Decode`. All mutation is on per-call slices (`symbols`, the `out` accumulator, `ids[:0]` in `fuseUnknowns`, the heap), and `merge` returns a slice that never aliases caller-visible data. The doc comment's concurrency claim holds. The shared slices from `Codebook`/`CodesFor` are M0 and out of scope, but they are documented as shared-and-must-not-be-modified.
- **Corpus coverage.** Confirmed present in `testdata/tokenizer_parity.json`: the 24 added tokens, the prefix pairs, the scaffold, the codebook, the 256-option wide prompt (`"Support queue 0"`), a long `x` run, and the control-character cases that reach byte fallback (`\u001b` is not a single vocab token, so `"\u001b[31mred\u001b[0m"` exercises the `<0xXX>` path). Not covered, and not coverable with this tokenizer: `fuse_unk`, the `Split` pre-tokenizer, and any `tokenizer.json` other than the pinned one beyond four synthetic rejection cases — which is why the hardcoding in `normalize`/`preTokenize` has no test.
- **`TestWidePromptIsNotQuadratic`.** Meaningful: it uses the widest golden vector, fails if the fixture's widest vector drops below 8000 ids, re-checks the ids, and allows 5 s against a measured 17.7 ms. A regression to the naive O(n²) merge over tens of thousands of symbols would exceed that; a constant-factor regression under ~280x would not, and the absolute wall-clock bound is machine-dependent. Acceptable for its stated purpose.
- **`Fetch` mechanics.** Temp file in the destination directory plus `os.Rename` is atomic on POSIX, so a concurrent reader or a second `Fetch` is safe; a failed `io.Copy` removes the temp file. `Authorization` is only attached when a token is present, and Go's client strips it on a cross-host redirect (the CDN hop), so the token is not leaked.
- **The codebook cross-check.** `TestParityCoversEveryCodebookCode` resolves `<channel|>` and all 256 codes against the shisa tokenizer and compares them to ids audited on the gemma tokenizer, which is a real cross-revision check rather than a restatement.
- **Not done:** I did not re-run any of the validation commands (read-only review, no shell), did not recount the 1,051 vectors or 48,296 ids (the fixture is a single 1-line file larger than the read limit), and did not exercise `Fetch` against the network.

## Residual Risks

- **Hugging Face internals I could not verify here.** The `tokenizers` crate source is not on this machine and no shell is available, so three claims in this report rest on recollection: the `Merge` ordering (`rank`, then `pos`) that makes the leftmost tie-break correct, the `ByteFallback` behaviour on invalid UTF-8 byte runs, and whether Hugging Face errors or silently skips a merge whose concatenation is missing from the vocab (this package skips, preserving the file's ranks). The first is strongly supported by the parity run against a fixture that includes a merge-bearing repeated-symbol run; the other two are not supported by any local evidence.
- **The parity evidence itself is the thing under review.** The claim that the ids are byte-identical to Hugging Face rests on a fixture generated by a script that does not pin the revision and records no provenance. I verified that the fixture contains the adversarial cases and that the current cache's `main` equals the pin, but I did not reproduce the generation, so I cannot say the vectors in the tree today are the ones snapshot `8f21734b...` would produce.
- **No end-to-end check yet.** The tokenizer package is used only by tests at this commit (`readout.go` does not reference it), so the prompt-token check and the code-boundary check that are supposed to catch a tokenizer mismatch have not run against a served model in this port. A silently wrong tokenizer file would be caught by those checks in M2+, but only if the counts differ.
- **Hub behaviour under real conditions.** The `Fetch` and `Lookup` findings were reasoned from the code. Whether Hugging Face returns a 200 with a non-tokenizer body, or how its CDN behaves on a truncated chunked response, was not tested.
- **The gemma/shisa tokenizer equivalence.** `docs/PORT.md` claims the two repositories share the tokenizer and the tests pin `shisa-ai/shisa-de-2` while the served DE-2 model is `google/gemma-4-26B-A4B-it` (per `docs/READOUT-DE2.md`). The two `tokenizer.json` files in the local cache are not byte-identical (they differ by a few lines outside the sections I compared). I did not diff them fully; the code ids agree per the codebook test, but the general equivalence of the two files is not established by anything I read.
